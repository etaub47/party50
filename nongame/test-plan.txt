PARTY50 MASTER TEST PLAN
Drafted 2026-10-21

======================================================================
HOW TO USE THIS PLAN
======================================================================

Work through the phases in order. Phases 1-9 cover every code path. Phase 10
covers content (all 25 missions). Each phase fits in one sitting.

Each test has:
  ID        e.g. M-07, so you can log a failure in one word
  People    [1] = you alone (two browsers is enough)
            [2] = two devices or people
            [3] = three devices or people at once (save these for family time)
  Steps     what to do
  Expect    what should happen; exact on-screen text is in quotes

Record each result as PASS, FAIL or BLOCKED. For a FAIL, note what you saw
(screenshot if you can).

Code-path failures (Phases 1-9) may need real fixing time, so do them first.
Phase 10 failures are usually a JSON or SQL edit.

Do not reset between phases unless a phase says to. A messy database is
closer to party conditions.


LOCALHOST OR VERCEL?

Test on Vercel for anything involving a phone. Use localhost only to try a
fix at your desk.

- Phone cameras need HTTPS. A phone loading http://192.168.x.x:3000 cannot
  open the camera, so QR scanning on localhost only works from the laptop's
  own webcam.
- Printed QR codes point at party50.vercel.app, so on Vercel they behave
  exactly as at the party.
- Vercel preview deploys also work: since the 2026-10-21 scanner fix, a
  preview URL accepts the printed production codes and stays on the preview
  site. Good for testing a fix branch on phones before merging.
- The database is shared either way, so one reset at the end covers both.


======================================================================
FINDINGS TO DECIDE ON BEFORE TESTING
======================================================================

The code survey for this plan turned up the items below. F1 is already
fixed. The rest are judgment calls.

F1. Cooldowns fired outside the game. FIXED 2026-10-21
    (trigger_specific_cooldown.sql) and applied to Supabase. Verify with
    R-04 and C-01.

F2. Collusion, keypad attempt limits, the HQ gate, and admin RPCs (start,
    end, reset, trigger) are all enforced only in the browser, or callable
    by any signed-in client. Same "nobody opens devtools" class you already
    accepted (old README 17/19). Listed so the acceptance is explicit.

F3. Typing /scan/find/<tool-id> by hand grants a Tool without paying, and
    the balance can go negative. Printed codes for Tools use /scan/buy, so
    only reachable by URL-typing. Same accepted class as F2.

F4. A blocked team (missing tool, repeat trio, repeat pair): the first
    teammate to close the overlay deletes the whole team, and the others
    see "CONNECTION TERMINATED". Probably fine, but confirm you like it
    during M-tests.

F5. Keypad attempts are counted per player per mission, and the count
    survives abort and rejoin. For non-Hackers this never matters: one
    wrong guess fails the mission, and it can't be rejoined. It matters for
    a Hacker who uses 2 of 3 attempts, aborts, and rejoins with only 1 left.
    Decide whether that is intended (M-15).

F6. Ending the game mid-mission: end_game deletes active mission rows, and
    any reward insert in flight fails silently (RLS needs IN_GAME). By
    design, but worth seeing once (see L-08).


======================================================================
PHASE 0 - TEST SETUP AND TEMPORARY CONCESSIONS
======================================================================

Devices
- Laptop: HQ pages (Chrome) plus one player (a separate Chrome profile).
- Your phone: main player.
- Family phones or extra browsers: players 2 and 3.

Getting more players than you have devices
Every private/incognito window, separate browser profile, or browser with
site data cleared is a brand-new anonymous player. Each needs the party
passcode again. One phone with Safari, Chrome and a private tab = 3 players.

Party gate
Every browser first needs the party passcode at /gatekeeper (stored for 7
days). HQ needs the HQ passcode at /hq/login (24 hours).

Concession A - collusion caps (trio once ever, any pair at most 4 times)
- Phases 4-5: leave them ON, since M-tests check them. Use fresh identities
  to make new trios.
- Phase 10 (25 missions with the same few people): temporarily disable
  them. In the Supabase SQL editor, re-run check_team_collusion and
  check_pair_collusion with "RETURN FALSE;" added as the first line after
  BEGIN. Re-apply the originals from data/functions/ in the Final
  checklist.

Concession B - role-balance cap
register_player refuses a role once it leads the runner-up by 4. With many
test identities, rotate roles so you don't trip it by accident. You test it
on purpose in R-05.

Concession C - test credits and heat
Players start with 25 credits; Tools cost 30-80. To fund purchases or force
a heat lockout without playing for hours, add QA events by SQL:

  -- one-time setup
  INSERT INTO event (id, type, intel, heat, credits, description) VALUES
   ('0a000000-0000-4000-8000-000000000001','CONSEQUENCE',0,0,200,'QA credit grant'),
   ('0a000000-0000-4000-8000-000000000002','CONSEQUENCE',0,500,0,'QA heat spike');

  -- give one to a player (copy their id from HQ Monitor)
  INSERT INTO player_event (player_id, event_id)
    VALUES ('<player-id>','0a000000-0000-4000-8000-000000000001');

Each player can receive each QA event once (primary key). For the heat spike
use +500, not +100: cooldowns and other negative heat would cancel a smaller
spike. The Final checklist removes both rows.

Concession D - time-based features
- Global events last 5 minutes.
- Cooldowns fire at :00 and :30 (UTC cron; the minute is the same in any
  time zone).
- HQ pulse thresholds are 20 and 45 minutes.
Plan to have an idle stretch for C- and H-tests, or run them while doing
something else.

  Steps: Watch the bars as intel/heat/credits change in later phases.

  Steps: Open History with no events, then after events.
  Expect: "No mission events recorded." then cards with time, description,

  Steps: Player A registered on device 1. HQ Monitor, open A's dossier,
  Generate Recovery Token. Scan it with device 2 (which may have its own
  player B).
  Expect: "Syncing Field Identity..." then device 2 is player A, with all

REC-02 [2] Recovery of a mid-mission player
  Steps: Player A in an IN_PROGRESS mission. Recover A onto another device.
  Expect: The new device resumes the mission at the current step.

REC-03 [1] Recovery failure (never exercised before)
  Steps: After REC-01, scan the same recovery QR again from a third

  Expect: Overlay "Recovery Failed" / "Target player identity not found."
  CONFIRM retries, CANCEL goes home. No endless "Syncing" screen. The
  scanning device's own player is NOT deleted (the transaction rolls back).

REC-04 [1] Same device scans its own recovery QR
  Steps: Scan player A's recovery QR on A's own device.
  Expect: Goes home, nothing changes.

  Steps: A 4th identity scans the same mission after M-05.
